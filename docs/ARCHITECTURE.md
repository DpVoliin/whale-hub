# 架构与设计取舍

## 整体

```
                        ┌──────────── 你自己的服务器 ────────────┐
 手机采集器              │                                        │
  ├ 使用情况访问 ──┐      │  中枢 hub.py（单文件 / 零依赖）          │
  ├ 日历读取     ──┼─HTTPS─▶  ├ /ingest   收数据 → SQLite           │
  ├ 通知监听(健康)─┘  +证书 │  ├ 规则引擎   每 5 秒巡检                │
  └ 前台服务(自适应频率)    │  ├ 脱敏关卡   → /llm-preview 可核对      │
                           │  ├ /pending /ack  （投递队列）           │
                           │  ├ /remind 定点提醒 / /brief 简报        │
                           │  └ /today    终端取"现在关心什么"          │
                           └────────────────▲───────────────────────┘
                                            │ 同一把 token
 电脑挂件(desktop/) ──HTTPS────────────────┘
 屏幕时长/窗口切换/磁盘/内存
                                            │ 拉取
                                   会拿主意的嘴（本机，持有 API key）
                                            │ HMAC 签名
                                            ▼
                                     网关 webhook → 微信
```

## 决策算法（都在中枢，零依赖）

"要不要打扰、能不能再说、多久说一次"三件事全部用**纯标准库**实现，且随数据自动变好：

| 判据 | 算法 | 为什么不用简单办法 |
|---|---|---|
| 有料程度 | 个人基线：median + MAD 稳健 z，小样本收缩 z'=z·n/(n+k) | 固定阈值不认人 —— 300 分钟屏幕对一个人是异常、对另一个人是日常；均值/标准差会被离群日撑爆 |
| 去重 | **事实层**新颖度（`{事实键: 档位}`，值未跨档即无新信息） | 措辞层相似度失效：同一件事换 23 种说法时，字符 3-gram Jaccard 仅 0.00–0.35 |
| 重提醒 | 指数退避（50/100/200/400 分钟，上限 4 条/天） | 按"值每涨一档就再提"会在线性增长的指标上刷屏（坐 11 小时 = 22 条） |

- **尺度下限**：MAD 可能为 0（几天数值一样）→ 取 `max(MAD, 5%×中位数, 1)`，避免算出 `z=∞`。
- **完整性门槛**：上报条数不足、或数值低于物理下限的那天丢弃（"设备没跑"≠"他没用"）。
- **方向性**：只判"偏多"（屏幕/游戏/刷视频）或"偏少"（磁盘剩余），避免把"今天特别安静"当成新闻。
- **记忆与复盘都在本地库**：`episodes`（她说过什么/发生过什么）与 `feedback`（✓/✗）都只落
  自己服务器；**进模型的只是检索出来的那几条摘要**，不是整库。
- **反馈闭环（两种信号）**：`/feedback` → 说话层累进 Thompson 后验 → 每日上限与间隔随之变化。
  ① **手动** ✓/✗（w=1.0）是强证据；② **隐式**——她说完 30 分钟内主人回话=欢迎、主人在场却没回=打扰、
  主人不在场=**不记**（w=0.4~0.6）是弱证据。后验按**分数计数** `(1+Σw_ok)/(2+Σw_ok+Σw_bad)`，
  所以弱证据能推动学习、但压不过主人亲手点的（`feedback` 表的 `w`/`src` 两列，schema v4）。
  *一段诚实的履历*：早先这里写的是"此前只能拿他有没有动手机当代理指标"——当时嫌代理信号粗糙而放弃；
  实测发现**手动反馈根本等不到**（长期 0✓/0✗）→ 后验恒等于先验 0.5 → 她永远过不了闸门、
  整套自适应在饿着。于是把代理信号请了回来，但加了两道边界：**弱权重 + 不在场不记**。
- **两条数据路**：给模型的那份走 `llm_context`（**强制脱敏**，只给类别名 + 百分比）；给终端的那份走 `/today` 的 `care`（不模糊 —— 你自己的设备、你自己的 token）。

## 几件"被咬出来"的机制（每一项都对应一次真故障）

| 机制 | 咬人的那次是什么样 | 现在怎么防 |
|---|---|---|
| **schema 迁移框架**（`PRAGMA user_version` + 幂等迁移链） | 手写 `ALTER` 写在 `executescript` 里 → 第二次启动 `duplicate column name` → **init_db 整个中断、中枢起不来**，且它之后的建表语句全部没执行（`/today` 直接断连） | 迁移是**有序函数列表**、每个必须幂等、失败只报错不崩；`hubctl schema` 查版本；测试覆盖"老库 / 连跑三次 / 重放" |
| **跨模块字符串一致性测试** | 两边约定了一个字符串却没人比对过：① 桶名（说话层用机器本地时区、中枢固定 +8 → UTC 服务器下 **85% 的分钟都错位**，后验永远取不到）② 料分读的字段（读 `rain_prob`/`classes_today`/`screen_usage_minutes`，中枢给的是 `desc`/`classes`/`screen_total_minutes_today` → **不报错、永远算 0 分**） | `test_band_consistency.py`（一周逐分钟比对）+ `test_material_signals.py`（静态比对读的键 vs 给的键）。**静默失效是最贵的一类 bug**：不报错、只是能力悄悄归零 |
| **CI 失败也会自报病因** | CI 红但读不到日志（Actions 日志要仓库权限）→ 只能猜 | 工作流在构建失败时把 Gradle 报错摘成 **check-run 注解**（公开可读）；四次工具链升级全凭它拿到原文报错 |
| **发版自检**（`collector/tools/check_apk.py`） | 把**公开仓库源码**编的包当私包发了出去 —— 公开库里那些值是占位符（`DEFAULT_HUB=""` / `<domain>YOUR_SERVER_IP</domain>`）→ 装上去「没有地址 + 认不出证书」，上报全挂、数据在手机上排队 | 发之前读包里那几处关键值比一遍（固定域名/默认地址/证书是否等于服务器当前那张/签名指纹） |
| **推送前脱敏体检** | 公开仓库里出现真实 IP／token 的风险 | 推送脚本先扫公网 IP／各类 token／私钥头，**不过就不推**（自己写过示例里的真 IP，被它拦过一次） |
| **合成数据压测**（`tests/make_fake_history.py --density real` + `hub/tools/stress_report.py`） | 小库上永远看不到的性能问题：纯函数被调 14 万次、21 天 14 万行拉回 Python 逐行 `json.loads` | 180 天 41 万行 8.8 秒造出来，量函数与接口耗时对预算；**改算法必须证明结果不变**（两种算法逐项比对） |

## 代码结构：片段 + 合并（既好维护，又不丢"单文件"）

```
hub/
├── src/whalecare/          ← **真相**：按职责切成 13 个片段
│     00_header   10_core      20_timetable  30_rules    40_privacy
│     50_weather  60_analysis  70_care       80_persona  90_ext
│     95_scheduler 97_http     99_main
├── tools/build_single.py  ← 按序合并成单文件（带结构断言）
└── hub.py                 ← **产物**：部署/发布用这一个
```

**为什么是"片段 + 合并"而不是 Python 包**：卖点之一是"单文件、clone 即跑"，拆成包就没了。
片段合并（amalgamation，SQLite 就是这么做的）两头都保住：**读代码时按模块看，发出去还是一个文件**。

**等价性可以证明，不靠"感觉没坏"**：切分是在章节边界**纯机械切片**，所以

```bash
python3 tools/build_single.py     # 合并 → dist/hub.py
cmp -s hub.py dist/hub.py         # 与原文件**逐字节相同**
```

`build_single.py` 还会断言关键函数与 `Handler` 方法都在**模块级** —— 这条不是形式主义：
曾经把方法体抽成函数时留在 class 内部，后面的方法变成了它的嵌套函数（语法合法！），
`py_compile` 照样通过，但 Handler 上少了方法、接口直接崩。

**日常改代码**：改 `src/whalecare/` 里对应片段 → `build_single.py` → 部署 `hub.py`。
新增职责就加一个片段，合并顺序就是文件名前缀顺序。

## 为什么这么分

| 决定 | 原因 |
|---|---|
| **手机不放模型** | 端侧模型发热掉电、质量差；放服务器则"省电 + 好换 + 被系统冻了也不影响判断" |
| **中枢单文件、零第三方依赖** | 部署 = 放一个文件，永不因为依赖崩；出问题只看一个文件 |
| **热重启靠指纹比对** | 不用 kill 进程：`run.sh` 每分钟比对文件指纹，变了才重启。远程部署不会卡在"停不掉旧进程" |
| **投递队列用 peek + ack** | 真发出去了才标记；失败留队列下轮重试（不是"取走即算送达"，那样会丢消息） |
| **说话层与中枢分开** | 中枢只负责"算出该说什么事实"，**措辞由模型现场生成**；API key 留在说话层所在机器，不上服务器 |
| **事实与措辞分离** | 中枢给我的永远是"有单位的事实"（`短视频/视频: 96 分钟`），不是"话" |
| **模型挂了回落模板** | 宁可话朴素，也绝不漏提醒 |
| **两条数据路分开** | 给模型的那份强制脱敏（`llm_context`）；给你的设备那份不模糊（`/today` 的 `care`）—— 你自己的数据、你自己的 token，没必要对自己打码 |
| **挂件与采集同进程** | 电脑上只装一个 exe：挂件和采集器共享一份配置、一个开机自启，也不会出现"两个程序抢同一个文件" |

## 设计上的硬约束（都写进代码注释了）

1. **字段没写单位 → 模型说胡话**
   给模型 `{"短视频": 1, "社交": 2}`（意思是"分类下有 1 个 App"）时，模型读成"你只刷了 1 条短视频"。
   → 现在字段名自带单位（`*_minutes_by_category`）并附 `_unit_note`。

2. **累计值被求和 → 数字翻倍**
   App 每轮上报"当天累计分钟"，一天多次。按分类 `SUM` 会把同一段时间重复加（B站 96 被算成 154）。
   → 现在**每个 App 只取当天最新一次**再按分类相加。

3. **唯一索引吃数据**
   `UNIQUE(device, metric, ts)` 会把"同一批次、同一时刻"的多条 App 用量合并成一条（真丢数据）。
   → 改成普通索引，去重交给代码里的"同设备同指标同值 60 秒内丢弃"。

4. **"按文字去重"挡不住同义句**
   同一件事被反复说了五遍（"08:00 那节在 1 号楼 201" / "1 号楼 201 那节课八点"）。
   → 改成**按事实指纹去重**：数字集合 + 关键词集合。

5. **假动作**
   早期文案里有"递水 / 拉窗帘 / 拿走你的手机"—— 她是 AI，做不到。
   → 角色卡写死：动作只能是情绪或她真能做的。

6. **免打扰时段挡住测试**
   `WHALE_IGNORE_QUIET=1` 是留给调试的口子。

7. **增量 vs 累计**（电脑侧新增指标时踩到）
   "窗口切换次数"如果每轮发**增量**，中枢就得 SUM，而 SUM 又会被重报放大。
   → 采集侧一律发**当天累计**，中枢一律"取最新"，与 App 用时的口径统一。

8. **独立进程发微信会被上游拒**
   微信不是"纯 token 平台"，独立 CLI 进程拿不到会话上下文（会被当成限流拒掉半小时）。
   → 改走**网关的 webhook 直投**（HMAC 签名、`deliver-only`、零 LLM 成本）。

## 加固与可靠性（一轮锐评之后）

- **中继**：不给 CA 拒绝启动；失败落盘 + 后台退避补发；转发带 `s=`/`c=`
- **中枢**：只认 `X-Token` 头（`/api/mcu` 例外，为单片机留 query）、1MB 体积上限、240 次/分限流、
  原始文本默认不落库、调度状态落盘、自动保留策略、启动日志 token 打码
- **单片机**：独立 token 自动生成；协议支持序号 + 校验和（各字符 ASCII 之和 mod 256）
- **备份**：`hubctl backup/dump --encrypt`（AES-256-CBC + PBKDF2）

## 采集频率是自适应的

| 状态 | 节奏 |
|---|---|
| 正在用（亮屏/解锁） | 5 分钟，且**事件触发立刻补采** |
| 早上（起床后 3 小时，起床时间从睡眠数据推） | 5 分钟 |
| 睡前（推算入睡前 90 分钟 → 入睡后 45 分钟） | 5 分钟 |
| 上课时段（按本地课表判断） | 30 分钟 |
| 其余白天/下午/晚上 | 30 分钟 |
| 睡着 | 180 分钟 |

> 健康类数据**不走这个节奏** —— 通知监听是实时的，所以省电不会漏掉健康事件。
